# OCR vs OpenAI 이미지 공지 추출 비교

## 목적

상세 공지 페이지 본문이 이미지뿐일 때, 어떤 방식으로 텍스트를 추출하고 모집 기간을 파싱할지 비교합니다.

현재 SwimPulse 기준 관심사는 아래 3가지입니다.

- 비용을 얼마나 통제할 수 있는가
- 공공기관 모집안내 이미지에서 기간 추출 정확도가 충분한가
- 현재 `NoticeCrawlerService` 규칙 파서와 자연스럽게 연결되는가

## 비교표

| 방식 | 과금 방식 | 정확도 경향 | 운영 특성 | 장점 | 단점 | SwimPulse 적합도 |
|---|---|---|---|---|---|---|
| 로컬 OCR만 | API 요금 없음 | 이미지 품질이 좋으면 실용적, 작은 글씨/표/왜곡에 약할 수 있음 | 서버 CPU 사용, 설치와 튜닝 필요 | 가장 저렴함, 외부 전송 없음 | 한글 OCR 튜닝 필요, 실패 케이스 존재 | 중간 |
| OpenAI Vision만 | 호출 비용 발생 | 문맥 이해 포함이라 복잡한 안내문에 강한 편 | API 의존, 구현은 비교적 단순 | 표/안내문/문맥 해석에 유리 | 비용 지속 발생, 외부 전송, 지연 가능 | 중간 이상 |
| 외부 OCR API만 | 건당/이미지당 과금 | OCR 품질은 높을 수 있으나 문맥 해석은 별도 | 외부 API 연동 필요 | OCR 엔진 품질이 안정적일 수 있음 | 비용 발생, 후처리 규칙 필요 | 중간 |
| 로컬 OCR + 기존 규칙 파서 | API 요금 거의 없음 | 단순 모집안내 이미지에는 꽤 적합 | OCR 설치 후 현재 파서 재사용 가능 | 비용 최소, 기존 코드 활용도 높음 | OCR 결과가 깨지면 파서도 같이 실패 | 높음 |
| 로컬 OCR + OpenAI fallback | 평소 저렴, 실패 시만 비용 발생 | 전체 균형이 가장 좋음 | 분기 로직과 실패 기준 설계 필요 | 비용 절감 + 어려운 케이스 보완 | 구현 복잡도 증가 | 가장 추천 |
| OpenAI Vision + 규칙 파서 혼합 | 호출 비용 발생 | 높은 편 | API 응답에 의존 | 이미지 이해 + 구조화 후처리 결합 가능 | 결국 비용이 계속 듦 | 예산 있으면 가능 |

## 방식별 설명

### 1. 로컬 OCR만

예시:

- `Tesseract`
- `PaddleOCR`

특징:

- 별도 API 요금은 없습니다.
- 대신 서버에서 OCR 연산을 직접 수행하므로 CPU와 메모리를 사용합니다.
- 이미지 품질이 나쁘거나 글자가 작으면 결과가 깨질 수 있습니다.

적합한 경우:

- 비용을 가장 아끼고 싶을 때
- 공지 이미지 형식이 대체로 일정할 때

### 2. OpenAI Vision만

특징:

- 이미지 자체를 모델에 넘기므로 호출 비용이 발생합니다.
- 단순 OCR보다 문맥을 읽는 능력이 있어 표/안내문 해석이 유리할 수 있습니다.
- 다만 모든 이미지 처리에 매번 비용이 듭니다.

적합한 경우:

- 정확도 우선
- 예산 허용

### 3. 외부 OCR API만

예시:

- Google Vision OCR
- AWS Textract
- Azure OCR
- Naver CLOVA OCR

특징:

- OCR 품질은 좋을 수 있지만, 모집 기간 같은 도메인 해석은 별도 로직이 필요합니다.
- 보통 토큰 과금이 아니라 이미지/문서 단위 과금입니다.

### 4. 로컬 OCR + 기존 규칙 파서

흐름:

1. 상세 공지 이미지 다운로드
2. 로컬 OCR로 텍스트 추출
3. 현재 `NoticeCrawlerService`의 기간 파서에 텍스트 전달

장점:

- 현재 코드 재사용성이 높습니다.
- 비용이 거의 들지 않습니다.

주의:

- OCR이 틀리면 뒤 파서도 같이 실패합니다.

### 5. 로컬 OCR + OpenAI fallback

권장 흐름:

1. 먼저 로컬 OCR 수행
2. 텍스트가 충분하면 기존 규칙 파서 사용
3. 텍스트가 비어 있거나 품질이 너무 낮으면 OpenAI 호출

장점:

- 평소 비용을 크게 줄일 수 있습니다.
- 까다로운 케이스만 AI로 보완할 수 있습니다.

이 프로젝트에서 가장 현실적인 이유:

- 공공기관 모집안내는 형식이 반복되는 편이라 로컬 OCR로 커버 가능한 비율이 높을 가능성이 큽니다.
- 진짜 어려운 이미지만 fallback으로 보내면 비용 통제가 쉽습니다.

## SwimPulse 기준 추천

1순위는 `로컬 OCR + OpenAI fallback`입니다.

이유:

- 비용과 정확도의 균형이 가장 좋습니다.
- 현재 `NoticeCrawlerService` 규칙 파서를 그대로 살릴 수 있습니다.
- 이미지 본문만 별도 처리하면 되므로 기존 HTML 파싱 로직과 충돌이 적습니다.

차선책은 `로컬 OCR + 기존 규칙 파서`입니다.

이유:

- 구현과 운영이 가장 단순합니다.
- 예산이 거의 들지 않습니다.
- 다만 OCR 품질이 낮은 이미지에서 실패율이 올라갈 수 있습니다.

## 추천 구현 순서

1. 이미지 URL 수집
2. 로컬 OCR 1차 도입
3. OCR 추출 텍스트를 기존 기간 파서에 연결
4. 실패 케이스 로그 수집
5. 실패율이 높은 경우에만 OpenAI fallback 추가

## 한 줄 결론

SwimPulse에는 `로컬 OCR을 기본값으로 두고, 실패 시에만 OpenAI를 호출하는 혼합 전략`이 가장 적합합니다.
