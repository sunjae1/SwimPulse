# SwimPulse 포트폴리오용 문제 해결 사례 3가지

작성일: 2026-06-22

## 요약

SwimPulse에서 포트폴리오에 가장 설득력 있게 쓸 수 있는 사례는 아래 3가지다.

| 번호 | 문제 상황 | 핵심 해결 | 대표 수치 |
|---:|---|---|---|
| 1 | 위치 기반 수영장 후보 조회가 외부 API에 묶여 느리고 실패율 발생 | Redis 캐시, single-flight lock, 정규화 매칭, 인덱스 | VUS10 위치 검색 p95 `1452.77ms -> 9.84ms`, 실패율 `14.91% -> 0%` |
| 2 | 이미지 공지 OCR 때문에 공지 확인 요청의 꼬리 지연이 16초 이상 발생 | 요청 경로에서 OCR 제거, Redis queue 기반 백그라운드 OCR 보강 | p99 `13.37s -> 406.07ms`, max `16.65s -> 859.34ms` |
| 3 | 구독/알림에서 동시성, 중복 생성, 큐 유실, DB 커넥션 고갈 리스크 발생 | DB unique 제약, duplicate 재조회, afterCommit queue publish, worker recovery | 다중 구독 1100 iterations 실패율 `0%`, p95 `67.2ms` |

## 사례 1. 위치 기반 수영장 후보 조회 성능 개선

### 문제 상황

사용자가 `부천시청`, `부천역` 같은 기준 위치를 검색하고 주변 수영장 후보를 찾는 과정에서 Naver Local Search, geocode, reverse geocode가 반복 호출됐다.

초기 구조에서는 같은 검색어와 같은 좌표 요청이 반복되어도 외부 API를 다시 호출했다. VUS10 순간 부하에서는 외부 API rate limit 성격의 실패가 발생했고, p95 latency가 1.3~1.4초까지 올라갔다.

또한 DB에 이미 존재하는 pool 후보를 매칭할 때 전체 pool을 읽고 Java에서 반복 정규화/중첩 비교를 수행했다.

### 해결 방안

| 개선 | 내용 |
|---|---|
| API 책임 분리 | 기준 위치 검색, 좌표 변환, 주변 DB 조회, 외부 후보 검색을 별도 API로 분리 |
| Redis 캐시 | Naver Local Search, geocode, reverse geocode 결과를 TTL 기반으로 캐시 |
| single-flight lock | cold cache에서 같은 key 요청이 동시에 몰릴 때 첫 요청만 외부 API를 호출하고 나머지는 대기 후 캐시 재사용 |
| 정규화 컬럼 | 이름, 도로명주소, 지번주소의 normalized 컬럼을 저장 |
| 배치 매칭 | 후보 10개를 정규화한 뒤 `IN` 쿼리와 `HashMap`으로 매칭 |
| 인덱스 추가 | `normalized_name`, `normalized_road_name_address`, `normalized_lot_number_address`에 BTREE 인덱스 추가 |

### 기술 선택 이유

| 선택지 | 선택 이유 |
|---|---|
| Redis 캐시 | 외부 API 결과는 TTL이 명확하고, 백엔드 인스턴스가 늘어도 공용 캐시로 공유 가능 |
| DB 캐시 테이블 미사용 | 검색어/좌표 기반 임시성 데이터라 영속 테이블보다 Redis TTL 관리가 단순 |
| single-flight lock | cache stampede/thundering herd 상황에서 외부 API 중복 호출을 줄이는 데 효과적 |
| 정규화 컬럼 + 인덱스 | 문자열 변환 비용을 요청마다 반복하지 않고, DB 조회 조건을 명확히 만들 수 있음 |
| 전체 응답 캐시 미사용 | DB에 새 pool이 추가된 직후 `alreadyExists`, `matchedPoolId` 상태는 최신이어야 하므로 외부 API 결과만 캐시 |

### 수치화

VUS10 기준 Redis warm cache 적용 전후:

| 시나리오 | Before p95 | After p95 | Before 실패율 | After 실패율 | Before RPS | After RPS |
|---|---:|---:|---:|---:|---:|---:|
| 위치 검색 | 1452.77ms | 9.84ms | 14.91% | 0.00% | 11.56 | 48.73 |
| 수영장 후보 검색 | 1360.60ms | 48.37ms | 17.14% | 0.00% | 11.99 | 42.86 |
| 전체 탐색 흐름 | 1336.33ms | 25.62ms | 5.24% | 0.00% | 21.52 | 73.62 |

DB 후보 매칭 개선:

| 비교 | Before | After | 변화 |
|---|---:|---:|---:|
| Legacy 전체 조회 평균 | 34.46ms | 19.10ms | 44.57% 감소 |
| Legacy 전체 조회 p95 | 53.41ms | 36.37ms | 31.90% 감소 |
| Batch no-index p99 | 68.73ms | 21.10ms | 인덱스 후 69.29% 감소 |

### 포트폴리오 문장

위치 후보 조회에서 반복 외부 API 호출과 문자열 매칭 병목을 발견하고, Redis TTL 캐시와 single-flight lock, 정규화 컬럼 기반 배치 매칭으로 개선했다. 그 결과 VUS10 기준 위치 검색 p95를 `1452.77ms`에서 `9.84ms`로 줄이고, 실패율을 `14.91%`에서 `0%`로 낮췄다.

## 사례 2. 이미지 공지 OCR로 인한 꼬리 지연 개선

### 문제 상황

공공 체육시설 공지는 HTML 본문에 모집 기간이 텍스트로 없고 이미지 한 장만 있는 경우가 많았다. 이를 처리하기 위해 Tesseract OCR을 도입했지만, 초기에는 사용자가 `공지 확인`을 누른 HTTP 요청 안에서 OCR을 바로 실행했다.

OCR 자체는 필요한 기능이었지만, 이미지 처리 시간이 요청 스레드를 오래 붙잡았다. 일부 요청은 16~17초까지 늘어났고, 사용자 입장에서는 공지 확인 버튼을 누른 뒤 화면이 오래 멈추는 문제가 생겼다.

### 해결 방안

| 개선 | 내용 |
|---|---|
| HTML 우선 파싱 | 상세 HTML에서 rule 기반 기간 파싱을 먼저 수행 |
| 로컬 OCR 도입 | OpenAI 이미지 분석 대신 Docker 내부 Tesseract CLI 사용 |
| 요청 경로 OCR 제거 | HTTP 요청에서는 OCR을 실행하지 않고 필요한 작업만 큐잉 |
| Redis queue | OCR 보강 대상 notice id를 Redis queue에 저장 |
| 백그라운드 worker | `NoticeOcrWorker`가 큐에서 notice를 꺼내 OCR 수행 후 DB 보강 |
| OCR 결과 캐시 | 이미지 URL 기준 OCR 결과를 Redis에 캐시 |
| 단계별 metric | `source_fetch`, `detail_fetch`, `detail_rule_parse`, `background_ocr_enrich`, `ocr_extract` 측정 |

### 기술 선택 이유

| 선택지 | 선택 이유 |
|---|---|
| Tesseract CLI | 로컬 실행이라 OpenAI API 비용 없이 이미지 텍스트 추출 가능 |
| OpenAI fallback 제외 | 유료 API 비용과 운영 key 관리 부담이 있어 현재 단계에서는 비활성화 |
| Redis queue | 현재 알림 queue와 Redis 인프라가 이미 있어 도입 비용이 낮음 |
| RabbitMQ 미도입 | OCR 보강은 실패해도 사용자 요청 전체를 실패시킬 필요가 낮아, 초기에는 Redis queue로 충분 |
| 백그라운드 보강 | OCR 정확도와 속도는 개선 대상이지만, 사용자 응답 지연과 분리하는 것이 우선 |

### 수치화

같은 k6 시나리오에서 baseline과 개선 후 비교:

| 측정 | 요청 수 | 실패율 | 평균 | p95 | p99 | 최대 | 처리량 |
|---|---:|---:|---:|---:|---:|---:|---:|
| baseline multi | 213 | 0.93% | 349.66ms | 301.63ms | 13.37s | 16.65s | 3.52 req/s |
| after multi | 292 | 0% | 117.50ms | 275.29ms | 406.07ms | 859.34ms | 4.84 req/s |

개선 폭:

| 지표 | 변화 |
|---|---:|
| 평균 응답 시간 | 약 66.4% 감소 |
| p99 | 약 97.0% 감소 |
| 최대 응답 시간 | 약 94.8% 감소 |
| 처리량 | 약 37.6% 증가 |
| 실패 응답 | 2건 -> 0건 |

cold reset 후에도 긴 꼬리 지연은 줄었다.

| 측정 | p99 | 최대 |
|---|---:|---:|
| baseline multi | 13.37s | 16.65s |
| cold reset after | 1.52s | 2.23s |

### 포트폴리오 문장

이미지 공지 OCR을 요청 스레드에서 직접 실행하던 구조를 Redis queue 기반 백그라운드 보강 구조로 바꿨다. OCR 비용은 여전히 존재하지만 사용자 응답 경로에서 분리해 p99를 `13.37s`에서 `406.07ms`로 낮추고, 최대 응답 시간을 `16.65s`에서 `859.34ms`로 줄였다.

## 사례 3. 구독/알림 동시성 및 큐 안정성 개선

### 문제 상황

SwimPulse의 핵심 도메인은 사용자가 모집 기간 이벤트를 구독하고, 시작 전 브라우저 푸시 알림을 받는 것이다. 이 흐름에는 단순 API latency보다 동시성 안정성이 중요했다.

부하 테스트 과정에서 다음 문제가 드러났다.

| 문제 | 증상 |
|---|---|
| 같은 논리 이벤트 중복 생성 | 동시 요청이 같은 `registration_events`를 각각 만들 위험 |
| duplicate key 예외 노출 | unique 충돌이 500으로 사용자에게 노출될 수 있음 |
| unsubscribe 동시 실행 | 같은 row를 여러 요청이 동시에 삭제하면서 404/실패 가능 |
| lazy proxy no session | JPA lazy entity를 트랜잭션 밖에서 DTO 변환 |
| DB connection pool 고갈 | 큰 트랜잭션 + `REQUIRES_NEW` 중첩으로 Hikari pool 고갈 |
| Redis publish 시점 | DB commit 전에 queue push가 되면 worker가 row를 못 볼 수 있음 |
| Redis pop 후 worker 장애 | pop 후 crash 시 queue item 유실 가능 |

### 해결 방안

| 개선 | 내용 |
|---|---|
| event unique 제약 | `registration_events(pool_id, title, registration_starts_at, registration_ends_at)` unique |
| duplicate 재조회 | insert 충돌 시 새 트랜잭션에서 기존 event 재조회 후 재사용 |
| subscription unique 제약 | `subscriptions(user_id, event_id)` unique |
| idempotent unsubscribe | 삭제 대상이 없어도 no-op으로 처리 |
| 짧은 트랜잭션 | 큰 outer transaction 제거, 저장/조회 책임 분리 |
| ID reference 저장 | entity 전체 조회 대신 FK id 기반 reference 저장 |
| afterCommit publish | notification row commit 이후 Redis queue push |
| SENDING 상태 | worker가 pop한 row를 `QUEUED -> SENDING`으로 전이 |
| stale requeue | 오래된 `SENDING` 알림을 다시 `QUEUED`로 복구 |
| dedupe key | 같은 event/type/user 알림 중복 생성 방지 |
| Mock FCM | 부하 테스트에서는 실제 FCM 대신 mock client 사용 |

### 기술 선택 이유

| 선택지 | 선택 이유 |
|---|---|
| DB unique 제약 | 중복 방지 규칙을 코드 관례가 아니라 스키마 차원에서 보장 |
| duplicate key 재조회 | 같은 이벤트를 동시에 만들 때 한 요청만 insert하고 나머지는 기존 row 재사용 |
| `PESSIMISTIC_WRITE` 축소 | `pools` row를 넓게 잠그는 방식보다 실제 중복 대상인 `registration_events`를 직접 보호 |
| Redis queue 유지 | 현재 알림 규모에서는 RabbitMQ보다 구현/운영 복잡도가 낮음 |
| RabbitMQ 보류 | DLQ, ack, 재시도 운영 UI가 필요해질 때 전환 검토 |
| afterCommit | DB와 Redis queue 사이의 순서 불일치 방지 |

### 수치화

구독/알림 k6 결과:

| 테스트 | 요청/반복 | 실패율 | p95 | 핵심 결과 |
|---|---:|---:|---:|---|
| 같은 사용자 같은 이벤트 구독 | 540 iterations | 0.00% | 73.6ms | 중복 구독 없이 기존 구독 재사용 |
| 구독 생성 후 바로 해제 | 535 iterations, 1071 HTTP requests | 0.00% | 72.6ms | 동시 delete를 idempotent 처리 |
| 여러 사용자 같은 이벤트 구독 | 1100 iterations | 0.00% | 67.2ms | 같은 event row 재사용, 커넥션 고갈 없음 |
| 테스트 알림 queue 처리 | 339 iterations | 0.00% | 52.1ms | notification row 생성 + Redis queue push 정상 |
| 알림 목록 조회 포함 | 330 iterations, 667 HTTP requests | 0.00% | 48.7ms | 최대 223개 알림 목록까지 조회 안정 |

### 포트폴리오 문장

구독/알림 도메인에서 동시 이벤트 생성, 중복 구독, 큐 publish 시점, worker 장애 복구 문제를 부하 테스트로 발견했다. DB unique 제약과 duplicate 재조회, afterCommit Redis queue publish, `SENDING` 상태와 stale requeue를 적용해 VUS 기반 구독/알림 테스트 5종에서 실패율 `0%`를 확인했다.

## 아직 고도화가 필요한 부분

### 1. 알림 목록 pagination

현재 알림 목록은 사용자 알림이 많아져도 전체를 내려줄 수 있다. 테스트에서는 최대 223개까지 안정적이었지만, 실제 사용자가 오래 쓰면 수천 개까지 늘 수 있다.

개선 방향:

| 작업 | 이유 |
|---|---|
| `/api/notifications?cursor=...&limit=...` | 응답 크기와 DB 조회 비용 제한 |
| `notifications(user_id, created_at)` 인덱스 | 최신순 목록 조회 최적화 |
| k6에 목록 조회 전용 duration metric 추가 | 알림 생성 요청과 목록 조회 요청을 분리 측정 |

### 2. 알림 scheduler 대량 발송 시나리오

현재는 테스트 알림과 구독 API 중심으로 검증했다. 실제 운영에서 중요한 것은 특정 시간에 많은 구독자가 동시에 due 상태가 되는 상황이다.

개선 방향:

| 작업 | 이유 |
|---|---|
| due event seed 생성 | 특정 시간에 열리는 이벤트/구독자를 대량 생성 |
| scheduler tick duration 측정 | 알림 생성 job이 얼마나 걸리는지 확인 |
| queue drain rate 측정 | worker가 queue를 얼마나 빨리 비우는지 확인 |
| delivery lag p95/p99 대시보드화 | 사용자가 실제로 늦게 받는지 판단 |

### 3. RabbitMQ 전환 판단 기준 마련

현재 Redis queue는 초기 서비스 규모에서는 충분하다. 다만 아래 조건이 생기면 RabbitMQ를 검토하는 것이 맞다.

| 전환 조건 | 이유 |
|---|---|
| 알림 유실을 더 엄격히 막아야 함 | RabbitMQ ack/requeue가 기본 기능 |
| 실패 알림을 DLQ로 모아 운영해야 함 | RabbitMQ dead-letter queue 활용 |
| 워커를 여러 대로 늘려 처리량을 관리해야 함 | queue routing과 consumer 관리가 Redis list보다 적합 |
| 재시도 정책이 복잡해짐 | delay, TTL, DLX 설계가 쉬움 |

### 4. OCR 정확도 개선

OCR을 백그라운드로 옮겨 성능 문제는 줄였지만, OCR 텍스트에서 의미 있는 모집 기간만 정확히 뽑는 일은 계속 개선 대상이다.

개선 방향:

| 작업 | 이유 |
|---|---|
| OCR segment parser 고도화 | 재등록, 반변경, 신규접수 같은 의미 있는 기간만 추출 |
| confidence 산정 개선 | 사용자에게 자동 추출 신뢰도 표시 가능 |
| 관리자 수정 UI | 자동 파싱 실패 시 사람이 기간을 보정 |
| OCR 실패/성공 metric 분리 | 성능 문제와 정확도 문제를 구분 |

### 5. 대표 이미지 관리 고도화

최근 추가한 대표 이미지 보강은 `og:image -> favicon -> 기본 상어 로고` 순서로 동작한다. 아직 이미지 출처와 상태 이력은 별도 컬럼으로 관리하지 않는다.

개선 방향:

| 작업 | 이유 |
|---|---|
| `image_source`, `image_checked_at` 추가 | 이미지가 어디서 왔는지 추적 |
| 관리자 이미지 수정 기능 | favicon/default가 마음에 안 드는 시설 보정 |
| 네이버 이미지 API fallback 검토 | 공식 홈페이지 이미지가 없는 시설 보강 |
| 이미지 저작권/정확도 검토 | 자동 저장 전 운영 리스크 관리 |

### 6. 성능 회귀 테스트 자동화

현재 k6 결과는 수동 실행 중심이다. 포트폴리오에는 수치가 충분하지만, 운영 관점에서는 반복 가능성이 더 중요하다.

개선 방향:

| 작업 | 이유 |
|---|---|
| 주요 k6 시나리오 Makefile 또는 npm script화 | 매번 명령어를 길게 치지 않도록 정리 |
| 결과 JSON naming 규칙 고정 | before/after 비교 자동화 |
| CI nightly load smoke | 큰 변경 후 성능 회귀 조기 발견 |
| Grafana dashboard provisioning 유지 | 노트북/데스크탑/서버 환경 동기화 |

## 면접에서 받을 수 있는 질문과 답변 포인트

| 질문 | 답변 포인트 |
|---|---|
| 왜 Redis 캐시를 썼나요? | 외부 API 결과는 TTL 기반 임시 데이터이고, 여러 백엔드 인스턴스가 공유해야 하므로 Redis가 적합했다. |
| 왜 전체 응답 캐시가 아닌가요? | pool 생성/중복 상태는 DB 최신값을 반영해야 해서 외부 API 결과만 캐시했다. |
| 왜 OCR을 OpenAI로 하지 않았나요? | 비용과 key 운영 부담 때문에 1차로 로컬 Tesseract를 선택했고, 실패해도 사용자 요청을 막지 않도록 백그라운드화했다. |
| 왜 RabbitMQ가 아니라 Redis queue인가요? | 초기 규모에서는 Redis queue로 충분하고, DLQ/ack/retry 운영 요구가 커질 때 RabbitMQ를 도입하는 편이 합리적이다. |
| 왜 pessimistic lock 대신 unique 제약인가요? | 중복 방지 규칙은 데이터 모델 자체가 보장하는 것이 더 명확하고, 같은 pool의 모든 요청을 넓게 잠그지 않아도 된다. |
| p95와 p99를 왜 봤나요? | 평균은 좋아 보여도 OCR처럼 일부 요청이 17초까지 튀는 문제가 숨겨질 수 있기 때문이다. |

## 최종 정리

이 프로젝트의 강점은 단순 기능 구현보다, 실제 병목과 동시성 문제를 부하 테스트와 운영 지표로 확인하고 개선했다는 점이다.

포트폴리오에서는 아래 문장으로 묶는 것이 좋다.

```text
공공 수영장 모집 공지를 수집하고 사용자별 구독/알림을 제공하는 서비스에서,
외부 API 의존으로 인한 위치 검색 지연, 이미지 OCR로 인한 긴 꼬리 지연,
구독/알림 동시성 문제를 k6와 Grafana로 측정했다.
Redis 캐시와 single-flight lock, 백그라운드 OCR queue, DB unique 제약과 queue recovery를 적용해
주요 API의 p95/p99와 실패율을 수치로 개선했다.
```
